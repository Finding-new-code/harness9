# ADR-005: Capability Token Security Model & Permission Calculus

**Status:** ACCEPTED  
**Date:** 2026-08-31  
**Deciders:** Head of Engineering, Security & Systems Team  
**Scope:** Security Architecture (`src/security/tokens.py`, `src/security/guard.py`)  

---

## 1. Context & Problem Statement

Autonomous multi-agent systems often run worker subagents and tools with full process-level permissions. In an autonomous studio pipeline, this poses critical security risks:
1. **Privilege Escalation**: A compromised or hallucinating research subagent attempting to execute destructive tools (e.g. deleting files, calling payment endpoints).
2. **Directory Escapes**: Worker agents reading sensitive credentials (`~/.hermes/.env`) or writing files outside the designated project workspace.
3. **Data Exfiltration**: Uncontrolled network egress leaking private drafts or research dossiers to unauthorized remote endpoints.
4. **Token Tampering**: Subagents modifying payload dictionaries to grant themselves elevated roles or tools.

---

## 2. Decision & Architecture

We decided to implement a **Principle-of-Least-Privilege Capability Token Engine** (`src/security/`) enforcing mathematical permission intersection calculus and HMAC-SHA256 signing.

### 2.1 The Intersection Calculus
$$\mathcal{P}_{\text{child}} = \mathcal{P}_{\text{parent}} \cap \mathcal{P}_{\text{role}} \cap \mathcal{P}_{\text{workflow}}$$

Permissions are strictly monotonic non-expanding:
- `allowed_tools`: Derived by intersecting parent, role, and workflow tool sets.
- `allowed_write_paths` / `allowed_read_paths`: Confined to subpaths within parent directories.
- `allowed_network_hosts`: Intersected whitelist (with `OFFLINE_ONLY` support).
- `expires_at_utc`: Child cannot outlive parent ($t_{\text{child\_exp}} \le t_{\text{parent\_exp}}$).
- `delegation_depth`: Monotonically incremented, strictly bounded by `max_delegation_depth`.
- `delegation_lineage`: Append-only ancestor token ID trace.

### 2.2 Cryptographic HMAC-SHA256 Signing
- All capability tokens are signed using a master secret key:
  $$\text{Signature} = \text{HMAC-SHA256}(K_{\text{master}}, \text{CanonicalJSON}(\text{Payload}))$$
- Any tampering with subject IDs, roles, tool whitelists, or expiration dates invalidates the signature and triggers `TokenTamperedError`.

### 2.3 Runtime Sandboxing Guard (`SecurityGuard`)
- Enforces active runtime interception:
  - Validates token signature and expiration.
  - Rejects unpermitted tool calls (`PermissionDeniedError`).
  - Resolves absolute paths, catches path traversal (`../`, null bytes), and enforces jail confinement (`PathTraversalError`).
  - Blocks network sockets to unlisted domains (`NetworkEgressError`).

---

## 3. Consequences & Trade-Offs

### Positive Consequences
- **Mathematical Security Guarantee**: Impossible for any child agent or tool to gain permissions not held by its parent.
- **Sandboxed Execution**: Filesystem and network operations are jailed to project workspace and approved hosts.
- **Tamper-Evident**: Cryptographic signatures prevent payload forgery across distributed or multi-process workers.

### Negative Consequences / Mitigations
- **Context Passing Requirement**: Workers and tools must receive and pass capability tokens.
  - *Mitigation*: The `SecurityGuard` provides `@guarded_tool` decorators and `guard_context()` context managers that handle verification cleanly.
